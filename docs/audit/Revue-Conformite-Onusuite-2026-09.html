Note globale stricte

L'ampleur fonctionnelle est réelle et rare : 219 pages, 512 tables, 21 edge functions, une isolation multi-tenant sérieusement durcie, une chaîne d'empreintes NF525, un export FEC aux 18 colonnes réglementaires. Sur le périmètre couvert, l'application dépasse largement le stade de la maquette.

Mais la note est tirée vers le bas par trois constats que la largeur fonctionnelle masque. Un : quatre triggers de comptabilisation automatique sont mutuellement incompatibles avec le trigger d'immuabilité — la validation d'une facture lève une exception en base. Deux : la balance, le bilan et le grand livre rapatrient l'intégralité des lignes d'écriture dans le navigateur pour les agréger en JavaScript, sans filtre d'exercice ni pagination. Trois : le moteur de paie ignore les mécanismes qui constituent le cœur de Sage Paie — plafond de sécurité sociale, tranches, prorata, cumuls, régularisation progressive.

Autrement dit : l'app ressemble à Sage sur la carte des écrans, mais ne calcule pas comme Sage sur le noyau. L'écart n'est pas dans la surface, il est dans le moteur.

02 — Progression

Les cinq critiques de septembre sont soldés

L'audit du 3 septembre laissait cinq points bloquants ouverts. Vérification faite sur le dépôt : tous les cinq sont corrigés. C'est la meilleure nouvelle de cette revue.

Mot de passe Postgres en clair dans le runner de migrationsCorrigé

app/run-sql-migrations.mjs lit désormais DATABASE_URL ou PGPASSWORD depuis l'environnement et refuse de démarrer sans. Plus aucune chaîne de connexion versionnée.

129 tables en RLS allow_all USING(true)Corrigé

La migration 74_rls_generic_tenant_isolation.sql balaie dynamiquement pg_policies, supprime toute politique permissive sur une table portant tenant_id et la remplace par une isolation current_tenant_id(). La 84_rls_critical_fixes.sql complète, la 78 révoque anon. Les seuls USING (true) restants sont en FOR SELECT sur six tables de référence réellement globales — currencies, banks, legislation_packs, tax_rates, chart_account_templates, public_holidays. C'est le bon arbitrage.

Tenant actif non déterministeCorrigé

79_current_tenant_priority.sql remplace le UNION ALL … LIMIT 1 sans ORDER BY par une priorité explicite : en-tête x-tenant-id d'abord, GUC de session ensuite, les deux revalidés contre tenant_users avec status = 'active'. Le fallback « premier tenant trouvé » a disparu.

Secrets préfixés VITE_Corrigé

.env.example documente explicitement la règle, et npm run build exécute scripts/check-bundle-secrets.mjs qui échoue si un secret atterrit dans le bundle. Le build de cette revue est passé : « Aucun secret détecté ».

CI rouge, déploiement non conditionnéCorrigé

deploy.yml se déclenche sur workflow_run avec conclusion == 'success'. La suite passe intégralement en local : 1 226 tests verts, 13 ignorés, tsc -b sans erreur, oxlint sans erreur.

03 — Anomalie bloquante

La comptabilisation automatique ne peut pas s'exécuter

Le défaut le plus grave de cette revue n'est pas un manque : c'est une contradiction entre deux migrations, qui rend inopérant tout le chaînage gestion commerciale → comptabilité.

Le trigger d'immuabilité bloque les triggers de comptabilisationBloquant

La migration 76 pose un garde-fou sur journal_lines, en BEFORE INSERT — et pas seulement en UPDATE/DELETE :

-- 76_accounting_invariants_and_stock_rpcs.sql:48-67
IF v_entry_status = 'posted' THEN
  RAISE EXCEPTION 'Ligne d''écriture % validée (posted) — immuable…', v_entry_id;
END IF;
…
CREATE TRIGGER prevent_posted_line_modification
  BEFORE INSERT OR UPDATE OR DELETE ON journal_lines
  FOR EACH ROW EXECUTE FUNCTION prevent_posted_line_modification();

La migration 90 crée ensuite quatre triggers métier qui insèrent l'en-tête déjà en 'posted', puis ses lignes :

-- 90_missing_workflow_triggers.sql:176-181
INSERT INTO journal_entries (…, status, …)
VALUES (NEW.tenant_id, v_number, NEW.date, 'VT', 'posted', …)
RETURNING id INTO v_entry_id;

INSERT INTO journal_lines (…) VALUES   -- ⇠ lève l'exception
  (NEW.tenant_id, v_entry_id, '411000', …);

Conséquence. Les triggers étant AFTER UPDATE dans la même transaction, l'exception remonte et annule l'opération d'origine. Concrètement : valider une facture de vente, une facture d'achat, un encaissement ou un décaissement échoue en base — la facture ne passe même pas au statut validé. Quatre triggers touchés : create_journal_invoice, create_journal_purchase_invoice, create_journal_customer_payment, create_journal_supplier_payment.

Le seed_demo_data.sql est frappé de la même façon sur ses écritures 'posted'.

Pourquoi personne ne l'a vu. Les 1 226 tests s'exécutent en 4,6 secondes avec Supabase mocké dans 19 fichiers : aucun trigger n'est jamais exécuté. 88_trigger_tests.sql existe mais ne tourne pas en CI — et son propre scénario contourne le problème en insérant en 'draft' puis en passant à 'posted' par UPDATE, ce qui est justement le bon ordre.

Correction. Insérer l'en-tête en 'draft', insérer les lignes, puis UPDATE … SET status = 'posted' — le motif déjà appliqué correctement par trg_payroll_create_journal en 81_complete_workflow_triggers.sql:337. Alternative : restreindre le trigger à BEFORE UPDATE OR DELETE, mais on perd alors la protection contre l'ajout d'une ligne à une écriture déjà validée.

04 — Comptabilité

Face à Sage 100 : la structure y est, la méthode non

Le schéma de journal_lines est de facture Sage — account_general, account_tiers, lettrage_code, analytic_section_id, vat_code, echeance_date, piece_number. Le problème est que la moitié de ces colonnes n'est jamais alimentée par le moteur de comptabilisation.

Ce qui est au niveau du marché

Invariants garantis par la base, pas par l'applicationConforme

Équilibre débit/crédit par CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED, tolérance d'arrondi à 0,01. Immuabilité des écritures validées avec extourne obligatoire. Contrôle de période close. Numérotation atomique par compteur sur le journal. Unicité des numéros de pièce, facture, avoir et bulletin par tenant. C'est la bonne architecture — la plupart des concurrents SaaS posent ces règles en couche applicative, où elles se contournent.

FEC et NF525Conforme

L'export FEC produit les 18 colonnes réglementaires, CompAuxNum et Montantdevise compris. La 91_nf525_anti_fraud.sql implémente un journal d'événements inaltérable à chaînage de hachage SHA-256, avec clôture et empreinte annuelle. La structure est celle attendue par un certificateur.

Les écarts de méthode

Aucun compte auxiliaire : le grand livre tiers reste videBloquant

Le trigger de vente écrit '411000' dans account_code et account_general, et laisse account_tiers et third_party_id à NULL. Or getGrandLivreTiers() filtre sur .eq('account_tiers', …) et getAgedBalance() sur .not('account_tiers','is',null).

Résultat : le grand livre tiers et la balance âgée n'affichent rien pour les écritures générées automatiquement, c'est-à-dire pour l'essentiel du flux. Chez Sage, le compte auxiliaire client est la clé de toute la gestion du poste client — relances, lettrage, échéancier, DSO.

TVA mono-compte, mono-tauxBloquant

Une facture produit une seule ligne 4457000 pour NEW.vat_total, quel que soit le nombre de taux qu'elle porte. La colonne vat_code de journal_lines n'est jamais renseignée.

Conséquence directe : la CA3 ne peut pas être ventilée par taux (20 / 10 / 5,5 / 2,1), l'autoliquidation et l'intracommunautaire ne sont pas distinguables, et le rapprochement TVA collectée / base HT — le contrôle de cohérence de base d'un cabinet — est impossible. Sage éclate systématiquement par code TVA.

Comptes de produit et de charge figésMajeur

Toute vente va en 707000, tout achat en 607000. Aucun mapping par produit, famille, catégorie ou nature de charge — alors que la table products et le plan comptable existent. Un cabinet ne peut pas produire un compte de résultat exploitable si toutes les charges atterrissent en « achats de marchandises ».

Plan comptable français codé en dur malgré l'architecture multi-législationMajeur

L'application gère des legislation_packs, un country_code par tenant et des grilles fiscales paramétrables — mais les triggers de comptabilisation écrivent des comptes du PCG français en littéral. Un tenant SYSCOHADA ou djiboutien reçoit des écritures en 411/707/4457. La contradiction entre l'ambition affichée et l'implémentation est frontale.

Le bilan et la balance ignorent l'exerciceMajeur

getTrialBalance() et getBalanceSheet() (accounting.ts:243, 482) ne portent aucun filtre de date ni d'exercice. Ils agrègent toutes les écritures depuis l'origine du dossier. Il n'y a pas d'application des à-nouveaux aux états, pas d'affectation du résultat, pas de solde d'ouverture. Le « bilan » produit est un cumul historique, pas un bilan d'exercice.

Le classement se fait par chart_accounts.type en trois seaux — actif / passif / capitaux propres. Il n'y a ni colonnes brut / amortissements / net, ni rubriques normalisées, ni résultat de l'exercice en capitaux propres. La LiasseFiscalePage.tsx « génère » la liasse en appelant ces deux fonctions et en sommant les classes 6 et 7 : c'est un affichage, pas un CERFA 2050-2059.

Lettrage et immobilisationsMineur

Le lettrage automatique existe et fonctionne sur les lignes non lettrées. Les immobilisations gèrent le linéaire et le dégressif via un RPC calculate_depreciation, avec plans d'amortissement et cession. Manquent l'amortissement dérogatoire, le prorata temporis du premier exercice et la comptabilisation automatique de la dotation annuelle — trois attendus standard côté Sage Immobilisations.

05 — Paie

Face à Sage Paie : l'écart le plus large de l'application

C'est ici que la réponse à votre question est la plus nette. Non, les calculs ne sont pas identiques à Sage, et l'écart n'est pas un écart de paramétrage. Le moteur src/lib/payroll.ts tient en 264 lignes ; il ne modélise aucune des notions structurantes d'un bulletin français.

Ce que fait réellement le moteur

Deux modes. En fallback, des taux 2024-2025 en dur appliqués à plat sur le brut. En mode grille, une boucle sur payroll_tax_grid_lines avec quatre types de ligne — percentage, bracket, fixed_amount, flat — et sept catégories agrégées. Deux raffinements corrects : l'assiette CSG/CRDS à 98,25 % du brut, et un plafonnement par ligne via cap_amount.

C'est un calculateur de cotisations proportionnelles. Sage Paie est un moteur de bulletin avec états de cumul.

Les douze mécanismes absents

  • Plafond de sécurité sociale absent
    Ni PMSS, ni plafond mensuel, ni proratisation du plafond. Toutes les cotisations plafonnées sont calculées sur le brut intégral : au-delà de 3 925 € mensuels, chaque bulletin est faux.
  • Tranches T1 / T2 absent
    calculateBracket() gère un barème progressif générique, mais aucune notion de tranche indexée sur le plafond. La retraite complémentaire AGIRC-ARRCO est inapplicable — le terme n'apparaît nulle part dans le dépôt.
  • Réduction générale de cotisations patronales absent
    Aucune trace de « réduction générale » ni de coefficient Fillon. Pour un employeur au voisinage du SMIC, c'est le poste patronal le plus important — et il est purement et simplement omis.
  • Prorata d'entrée, de sortie, d'absence absent
    Zéro occurrence de « prorata » dans tout le dépôt. Un salarié embauché le 12 du mois est payé plein mois. Aucune méthode de retenue pour absence — ni horaire réel, ni jours ouvrés, ni trentième.
  • Cumuls annuels et régularisation progressive absent
    Le bulletin est calculé isolément, sans mémoire des périodes précédentes. La régularisation progressive des plafonds — obligatoire en paie française — n'existe pas. Les écarts d'arrondi et de plafond ne sont jamais rattrapés.
  • Net imposable et CSG déductible / non déductible absent
    La CSG est agrégée en un seul montant. Sans la scission 6,8 % déductible / 2,9 % non déductible + CRDS, le net imposable est incalculable — et sans net imposable, la DSN et le prélèvement à la source sont invalides.
  • Heures supplémentaires : exonération et majorations différenciées partiel
    Taux unique de 1,25 sur gross / 151,67. Pas de palier à 50 % au-delà de la 8ᵉ heure, pas d'exonération salariale plafonnée à 7 500 €/an, pas de déduction forfaitaire patronale.
  • Conventions collectives absent
    Aucune notion de convention, de classification, de coefficient ni de minimum conventionnel. Sage livre des paramétrages par IDCC ; ici, rien ne rattache un salarié à une branche.
  • Ancienneté, 13ᵉ mois, primes conventionnelles absent
    Les primes passent par payroll_variable_elements saisis manuellement. Aucun calcul automatique d'ancienneté ni de prime récurrente.
  • Indemnités de rupture et solde de tout compte absent
    Ni indemnité légale, ni indemnité compensatrice de congés payés au moment du solde, ni certificat de travail lié au calcul.
  • Maintien de salaire, IJSS, subrogation absent
    Les arrêts maladie n'ont aucun effet sur le calcul du bulletin.
  • Bulletin clarifié réglementaire partiel
    La table pay_slip_clarified stocke des lignes libres. Le modèle imposé — regroupement par risque, colonne « allègements de cotisations », mention du montant net social — n'est pas respecté.
Deux effets de bord dans le code existantBloquant

Impôt sur le revenu hors PAS. queries/payroll.ts:231 passe taxRate: 10 en dur pour tous les salariés lors de la génération d'un bulletin. Le taux transmis par la DGFiP n'est jamais lu, alors que employees pourrait le porter. Chaque bulletin généré applique 10 % au lieu du taux personnalisé.

Assiette d'impôt erronée. taxableGross = totalGross + transportAllowance (payroll.ts:117). L'indemnité de transport, exonérée dans la limite légale, est ici ajoutée à l'assiette imposable au lieu d'en être exclue. Le sens est inversé.

La table payroll_tax_grid_lines est bien conçue et le paramétrage par pays est la bonne intuition. Mais un modèle à quatre types de ligne et une assiette parmi cinq ne peut pas représenter un plafond proratisé, une tranche indexée, un cumul ni une régularisation. Passer de 3,5 à 8 sur cet axe demande une refonte du moteur, pas des données.

06 — Gestion & projets

Face à Odoo et aux outils de projet

Gestion commerciale, achats, stock, production — Odoo 17

C'est le domaine où la comparaison est la plus flatteuse. Le three-way matching (86_three_way_matching.sql), la valorisation de stock déversée en comptabilité (87_stock_valuation_to_gl.sql), les gammes avec postes de charge, machines et outillages, les ordres de sous-traitance, le MRP avec propositions et prévisions, les nomenclatures multi-niveaux : l'ensemble correspond à ce qu'Odoo couvre en Manufacturing et Inventory. Les triggers de la migration 90 automatisent la chaîne réception → stock → statut de commande, la sortie sur bon de livraison, et l'entrée après contrôle qualité.

Les écarts sont ciblés : traçabilité série/lot présente en tables mais peu exploitée dans les mouvements, pas de règles de réapprovisionnement min/max par entrepôt, pas de stratégies de put-away, pas de landed costs. Le CRM couvre opportunités, activités et campagnes mais reste en deçà d'Odoo CRM sur le scoring et les séquences automatisées.

Gestion de projet — ClickUp, Monday, Asana

Le module le plus abouti de l'application, et de loin. Dix-huit routes, quarante-six composants dédiés : Gantt éclaté en cinq composants, Kanban, mind-map, burndown, tableau croisé dynamique, vue charge, timeline, calendrier, chat, documents, tâches récurrentes, minuteur, chatter par tâche, colonnes dynamiques typées. C'est la parité de surface avec ClickUp, avec une intégration que ClickUp n'a pas : les projets sont branchés sur la comptabilité analytique et les budgets.

Ce qui manque pour rivaliser réellement : les dépendances entre tâches de projets différents, le chemin critique, la capacité par ressource avec calendriers d'absence — alors même que le module RH tient déjà ces données —, et le temps réel multi-utilisateur (les vues sont chargées par requête, sans souscription).

07 — Fondations

Performance, tests, intégrations

Les états financiers sont agrégés dans le navigateurBloquant

getTrialBalance(), getTrialBalanceFiltered(), getBalanceSheet() et getGeneralLedger() exécutent un select sur journal_lines sans limit, puis somment dans une Map JavaScript. Sur l'ensemble du dépôt : 29 .limit() pour 1 152 fonctions de requête, et 291 select('*') sans borne.

Deux risques distincts. Truncation silencieuse : si PostgREST applique une borne de lignes, la balance est calculée sur un sous-ensemble et affiche un résultat faux sans erreur — le pire mode de défaillance possible pour un logiciel comptable. Effondrement : un dossier PME sur trois exercices dépasse aisément 100 000 lignes ; l'onglet ne tient pas. Sage adresse des dossiers à plusieurs millions de lignes parce que l'agrégation est faite par le moteur SQL.

La correction est mécanique et le socle existe déjà : 39 RPC sont appelés depuis le front, et 77_financial_aggregations_and_pagination.sql pose la brique. Il reste à basculer les quatre états sur des fonctions GROUP BY côté base, paramétrées par exercice.

Une suite de tests qui ne teste pas la baseMajeur

1 226 tests verts en 4,65 secondes. Cette vitesse est la preuve qu'aucun test ne touche Postgres : 19 fichiers mockent Supabase, et sur les assertions, 923 vérifient qu'un mock a été appelé contre 865 qui vérifient une valeur. Les tests métier réels — hr-payroll-business, logic-business — sont de bonne qualité et vérifient de vrais calculs, mais ils valident le moteur tel qu'il est écrit, pas tel qu'il devrait être : aucun n'aurait détecté l'absence de plafond SS.

Les 323 triggers, les 218 fonctions PL/pgSQL et les 2 208 politiques RLS ne sont couverts par aucun test exécuté. C'est exactement pour cela que l'anomalie bloquante de la section 03 a survécu. 88_trigger_tests.sql existe : il faut le brancher sur la CI avec une base éphémère.

Détail d'hygiène : six fichiers .bak et .bak2 traînent dans src/lib/__tests__/ et dupliquent des suites entières.

TypeScript sans strictMajeur

tsconfig.app.json ne contient aucune directive strict, et aucun fichier de configuration n'en hérite. strictNullChecks et noImplicitAny sont donc désactivés, avec 1 884 any explicites dans le code source. Pour une application qui manipule des montants, c'est le filet de sécurité le plus rentable qui n'est pas tendu — d'autant que les autres réglages exigeants (noUnusedLocals, noUnusedParameters, noFallthroughCasesInSwitch) sont, eux, activés. L'omission ressemble à un oubli plutôt qu'à un choix.

Quatre intégrations réglementaires en « mode simulation »Majeur

transmit-dsn, submit-vat-return, submit-e-invoice et request-signature retournent mode: "simulation" et un message explicite lorsque l'API cible n'est pas configurée. Le comportement est honnête et bien codé — mais il signifie que la DSN vers net-entreprises, la télédéclaration CA3, Chorus Pro / PEPPOL et la signature Yousign / Universign ne sont pas raccordées. Les dix-sept autres edge functions sont des implémentations réelles ; celles-ci sont des façades en attente de contrat.

Chunk d'entrée de 1,28 MoMineur

324 ko compressés à l'entrée, avant les 279 ko de queries et les 280 ko de react-vendor. Le découpage par route existe pourtant. Les gros modules d'export — xlsx 489 ko, pdf 466 ko — mériteraient un import() dynamique au clic plutôt qu'un chunk préchargé.

Numéros de migration en doublonMineur

Six collisions — 38, 44, 71, 87, 88, 89 — dont 87_critical_business_functions face à 87_stock_valuation_to_gl. Le runner avertit mais applique quand même, dans l'ordre lexicographique. L'ordre d'exécution devient dépendant du nom de fichier, ce qui est fragile pour des migrations qui se recouvrent.

Trigger d'équilibre en FOR EACH ROWMineur

check_journal_entry_balance relance un SUM complet sur les lignes de l'écriture à chaque ligne insérée. Sur une écriture de dix lignes, dix agrégations. Sur un import FEC de 100 000 lignes, le coût devient quadratique par écriture. Un FOR EACH STATEMENT sur les écritures touchées ferait le même travail en une passe.
