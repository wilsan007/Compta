# Vague W4 — la paie et les RH : une seule façon de compter un mois — 26 septembre 2026

> **Objet.** Fermer les six défauts **RH-05 → RH-10** du
> [plan correctif](PLAN-CORRECTIF-COMPLET-ET-VERIFICATION-2026-09-24.md) (§W4) :
> quatre conventions mensuelles contradictoires, un import qui échoue cinq mois
> sur douze, des notes de frais qui entrent en paie pour zéro, sans TVA ni
> écriture, un congé à cheval sur deux mois omis, et des titres restaurant qui
> doublent au réimport.
> **État d'entrée.** Mesuré sur base neuve (226 migrations, sans la 256) :
> * **RH-05** — quatre diviseurs pour la même paie : `weekly_hours × 4,33`
>   (retard), `/ 30` (congé sans solde **et** absence non justifiée),
>   `/ 151,67` (heures supplémentaires), `/ 21` (front, congé sans solde).
>   Pour un salaire de 3 000 € : **100,00 €** la journée par la base,
>   **142,86 €** par le front — **43 % d'écart** pour la même absence ;
> * **RH-10** — `payroll_variable_elements` n'a **qu'un index unique** : sa clé
>   primaire (`id`). Rien ne relie un élément à son document source ;
> * **RH-07 / RH-08** — **0 écriture** de note de frais dans tout l'historique
>   (`journal_entries` filtré sur `EXPENSE-%`) : le trigger n'écrit qu'un
>   élément de paie… et le front, lui, lit `Number(exp.amount)`, une colonne qui
>   n'existe pas sur `expense_reports` (`total_amount`), donc **0 €**.
> **Livré** : migration **256** (`app/sql/256_payroll_periods_amounts_divisor.sql`,
> 11 fonctions, 1 index unique, 2 paramètres), suite **256** (8 scénarios verts),
> correction du front (`src/lib/payrollPeriods.ts` + les quatre importeurs de
> `src/lib/queries/leavesAbsences.ts`), **17 tests Vitest** nouveaux, câblage CI.

## 1. Ce que la 256 corrige, et où

| Défaut | Ce qui se passait | Ce qui se passe |
|---|---|---|
| **RH-05** — quatre conventions | retard `salary / (weekly_hours × 4,33) / 60` ; congé sans solde `salary / 30` ; absence non justifiée `salary / 30` ; heures sup `salary / 151,67` ; front `salary / 21` | **`payroll_divisor(tenant, unité)`** : un PARAMÈTRE par société (`payroll_legal_parameters`, société puis global), avec un défaut **calculé** — `35 × 52 / 12 = 151,6667 h`, `5 × 52 / 12 = 21,6667 j` — et le « trentième » laissé à `company_settings.absence_method`. Les trois chemins de la base et le front lisent **la même** valeur |
| **RH-06** — les bornes de période | `.lte('date', '<période>-31')` : PostgreSQL refuse « 2026-04-31 » (22008) — février, avril, juin, septembre, novembre n'importaient **rien** | `periodBounds(period)` calcule le **dernier jour réel** (`new Date(Date.UTC(y, m, 0))`) ; les quatre requêtes du front l'utilisent |
| **RH-07** — notes de frais à 0 € | front : `Number(exp.amount)` → `NaN` → `null` ; base : `total_amount` mais aucun effet comptable | front : `total_amount` (et la période de la note, pas `submitted_at`) ; base : élément **`expense_reimbursement`** (le type que `calculate_payslip` **ajoute** au net — en `other`, la note était **retranchée**) |
| **RH-08** — ni TVA ni écriture | aucune | écriture `D charge HT + D TVA récupérable / C 421 (salarié)`, comptes **du paramétrage** (`payroll_account`, `vat_account_mapping`) — avec la **correspondance canonique du taux** (FR20 → 445661), jamais un régime particulier (voir §4) |
| **RH-09** — congé à cheval | « contenu dans la période » (`start_date >= début AND end_date <= fin`) : un congé du 28/04 au 03/05 n'entrait dans **aucun** bulletin | **intersection** (`periodOverlapFilter`) : il entre dans les **deux** |
| **RH-10** — titres restaurant doublés | aucune garde : relancer l'import doublait les éléments | index unique **`uniq_payroll_element_source`** `(tenant, salarié, période, type, source, source_id)` + `ON CONFLICT DO NOTHING` dans les **six** alimentations de la base + `upsert(…, ignoreDuplicates)` dans les **quatre** du front |

**Deux défauts trouvés en écrivant les tests, pas dans l'audit** : (a) le front
écrivait des types d'éléments que le moteur de bulletins **ne lit pas** —
`absence` (ignoré), `meal_voucher` au singulier (ignoré), `other` (compté comme
**retenue**) ; (b) le compte de TVA de la note de frais tombait sur
**445668 — autoliquidation** au lieu du compte du taux. Les deux sont corrigés
et mesurés (T06, et les tests Vitest sur les types).

**Le test T06 a fait tomber une erreur commise DANS cette vague** : la première
résolution du compte de TVA prenait « le taux le plus élevé » —
`ORDER BY rate DESC LIMIT 1` — et trois lignes partagent le taux 20 %
(`FR20 → 445661`, `UE → 445667`, `AUTOLIQ → 445668`). PostgreSQL en rendait une
**au hasard** : la note de frais de T06 est partie sur **445668
(autoliquidation)**. C'est exactement le piège que la 219 avait corrigé pour la

résolution applique désormais la même règle qu'`pos_vat_account` : la
**correspondance canonique du taux** d'abord (`vat_code_for_rate`), les régimes
particuliers en dernier, puis le taux courant du pack.

## 5. Les limites, dites

* **Une seule source d'heures supplémentaires, pas encore.** Le front
  (`importTimesheetElements`) les calcule par « heures au-delà de 8 h par
  jour » ; la base (`sync_timesheet_to_payroll`) lit `timesheets.overtime_minutes`,
  alimenté par le pointage. Les deux écrivent le **même** type (`overtime`) et le
  **même** document source : la contrainte les empêche de compter deux fois
  **dans le même mois**. Si un pointage d'avril est importé dans le lot de mai,
  les deux lignes portent des périodes différentes et coexistent — c'est le lot
  **W5** (« un seul moteur par grandeur ») qui doit supprimer le calcul du front,
  pas cette vague.
* **Le diviseur « jours » change une valeur historique.** Il valait `21` dans le
  front : il vaut désormais `5 × 52 / 12 = 21,6667` par défaut (ou `30` si
  `absence_method = 'thirtieth'`, ou la valeur paramétrée). Une société qui
  tenait à `21` doit **poser le paramètre** — c'est le but : la convention
  devient un choix explicite au lieu d'un littéral.
* **Les bulletins déjà calculés ne sont pas recalculés.** Les lignes de paie
  existantes sont des pièces : elles gardent leurs montants. Un bulletin
  recalculé après la 256 utilise le nouveau diviseur — et le rejeu d'un import
  ne crée plus de doublon, mais **ne corrige pas** un doublon déjà intégré
  (`integrated = true`), qui reste à traiter à la main.
* **Le diviseur horaire suit le contrat.** Le défaut est calculé sur
  `employees.weekly_hours × 52 / 12` (35 h → 151,6667 ; 39 h → 169) ; le
  paramètre de société, s'il est posé, l'emporte pour tout le monde. Une société
  qui a plusieurs conventions horaires doit poser des paramètres par période
  (`valid_from`), ce que la table permet déjà.
* **La localisation n'est pas faite.** Les paramètres sont semés en `FR` ; le
  mécanisme est neutre (chaque pays lira ses lignes), mais les codes et les
  valeurs semés sont français. C'est la décision `D-11`, ouverte.
* **La TVA d'une note de frais est celle de la note** (`total_vat`), pas une
  ventilation ligne à ligne : le débit de TVA est unique, avec le taux des lignes
  (`expense_report_lines.vat_rate`) pour choisir le compte. Un document mêlant
  plusieurs taux produit **un seul** compte de TVA — celui du taux le plus élevé
  constaté. Le refus explicite n'intervient que si la TVA dépasse le total
  (T08).
* **Le remboursement n'est pas décaissé ici.** L'écriture crédite le salarié
  (421) ; le paiement appartient aux écrans de règlement, comme l'avoir de la
  255.
* **`payroll_divisors()` exige une société active.** Le front l'appelle avant
  chaque import : sans jeton (aucune société), la fonction **refuse** au lieu de
  rendre un diviseur de zéro — un diviseur nul aurait produit des taux à 0 sans
  le dire.
