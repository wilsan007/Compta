## 3. Les trois migrations

### `257_edge_columns_and_errors.sql` — les colonnes que les fonctions croyaient écrire

La règle : on **ajoute** une colonne seulement si la notion manque au schéma ;
là où un équivalent existait, le code est aligné et **aucune** colonne n'est créée.

| Table | Colonnes ajoutées | Ce que cela ferme |
|---|---|---|
| `leave_requests` | `manager_comment` | le refus d'un congé depuis le mobile ne pouvait pas porter son motif (`MobileApproval.tsx:45`) |
| `bank_transactions` | `matched_line_id` (**clé composite** vers `journal_lines`) | le rapprochement manuel ne marquait rien (`banking.ts:101`) |
| `bank_transactions` | `provider_transaction_id` (+ **unicité** `(société, compte)`) | chaque synchronisation réimportait les mêmes opérations (`EF-04`) |
| `collection_reminders` | `days_overdue`, `sent_at`, `email_sent`, `last_error` | la relance n'était jamais tracée (`EF-02`) |
| `collection_reminders` | `reminder_level` **1→4**, `status` + `pending`/`failed`, invariant `email_sent ⇒ sent_at` | le niveau 4 (« procédure de recouvrement ») **ne pouvait pas être enregistré** ; un envoi en cours ou en échec était refusé par le `CHECK` |
| `notification_email_queue` | `metadata` | l'échec de paiement Stripe n'était jamais mis en file |
| `electronic_signatures` | `provider`, `provider_signature_id` (+ unicité), `status`, `signers`, `initiated_at` | la demande Yousign n'était **jamais enregistrée** (`EF-07`) |
| `invoices` | `e_invoice_status`, `e_invoice_platform`, `e_invoice_submitted_at`, `e_invoice_id` (+ unicité) | le dépôt Chorus Pro était transmis puis oublié → **double envoi** (`EF-05`) |

Alignements **sans** nouvelle colonne : `webhook_delivery_logs.http_status` →
`response_code` ; `bank_connections.provider_requisition_id` →
`provider_connection_id` ; `link_url` / `user_id` → `metadata` (jsonb, avec
`initiated_by`).

Reprise des données existantes : `electronic_signatures.status` est posé
(`signed` si `signature_hash`, sinon `pending`) — aucune ligne effacée.

### `258_payment_reminders_idempotent.sql` — une relance part une fois

1. **Reprise** : les relances en double du même niveau sont ramenées à une — la
   première (dont l'envoi est prouvé) est conservée, les suivantes passent à
   `cancelled` avec la raison en `notes`. Aucune suppression.
2. **Unicité partielle** `(tenant_id, invoice_id, reminder_level) WHERE status <> 'cancelled'` :
   le doublon devient impossible.
3. `claim_collection_reminder(…)` rend un identifiant, ou `NULL` si un envoi de
   ce niveau est déjà prouvé — **ou en cours**. Un échec antérieur, lui, se
   reprend (`status = 'failed'` → `pending`).
4. `finalize_collection_reminder(…)` : **un seul chemin** qui dit « envoyée »
   (avec `now()`) ou « en échec » (avec l'erreur du prestataire), depuis
   `pending` uniquement.
5. Droits : les deux RPC sont révoquées d'`anon` et `authenticated`, accordées à
   `service_role` (le cron). Un écran ne peut pas se déclarer « relance envoyée ».

### `259_placebos_removed_or_wired.sql` — un écran ne peut plus tamponner un succès

Un déclencheur générique (`refuse_client_success_stamp`, colonne en `TG_ARGV[0]`)
refuse à `anon`/`authenticated` **tout changement** de :

* `vat_returns.edi_status` (la télédéclaration — `TVA-01`),
* `invoices.e_invoice_status` (le dépôt — `EF-06`),
* `bank_connections.last_sync_at` (la synchronisation — `EF-03`).

Un formulaire qui recopie la valeur existante passe ; le `service_role` (la
fonction Edge, après un appel réel) passe. Sans JWT (migration, superutilisateur,
cron SQL) la porte est ouverte.

| `validate-vat-vies` | **Paramètres → Société**, à côté du numéro de TVA | idem : la source est nommée (`VIES` ou locale) |
| `verify-iban` | **Comptes tiers → onglet Banques**, sous l'IBAN | « IBAN valide (format, longueur du pays et clé ISO 13616) », ou le motif du refus |
| `request-signature` | **Documents du salarié**, action par pièce **hébergée** | « Demande enregistrée chez le prestataire — identifiant … » ; l'écran **ne marque pas** la pièce « signée » (seule une signature effective le fera) |
| `generate-pdf` | **aucune** — retirée du déploiement (défaut `D-4`) | — |

Le composant `VerificationLine` est partagé (`app/src/components/VerificationLine.tsx`) :
un identifiant invalide est montré comme tel, avec son motif, jamais présenté
comme vérifié.

### 8.4 `generate-pdf` : durcie et **non déployée** (le défaut que l'audit prévoyait)

`AUD-H03` relevait trois défauts cumulés : HTML fourni par le client (SSRF en
lecture **prouvée**), valeurs interpolées non échappées, et déploiement
`--no-verify-jwt` sans aucun appelant. La décision `D-4` reste ouverte, mais
l'audit indiquait déjà le défaut à appliquer : « à défaut : retirer de
`deploy-all-functions.sh` ». C'est fait, **et** le code est durci dans le même
mouvement :

* le paramètre `html` du client est **refusé** (`400 CLIENT_HTML_REFUSED`) : le
  document est construit par le serveur depuis la pièce enregistrée ;
* toutes les valeurs interpolées sont **échappées** (`escapeHtml`) ;
* deux tests tiennent la porte (sans jeton → 401 ; HTML client → 400 nommé).

### 8.5 Le déploiement cesse d'être « tout en `--no-verify-jwt` »

`deploy-all-functions.sh` déployait **les 20 fonctions** sans vérification de
jeton par la passerelle. Il distingue maintenant :

* **13 fonctions avec JWT vérifié par la passerelle** (défaut) — un appel sans
  jeton est refusé **avant** l'exécution ;
* **6 points d'entrée publics**, chacun avec sa garde propre : `auth-signup`
  (inscription), `cron-payment-reminders` (secret de cron),
  `handle-stripe-webhook` (signature Stripe), `outgoing-webhooks` (clé de
  service), `public-api` (clé d'API), `refresh-exchange-rates` (clé de service) ;
* **1 fonction non déployée** : `generate-pdf` (`D-4`).

### 8.6 Ce qui reste ouvert, et pourquoi

* **Aucun appel réel au réseau** n'a été exercé : la recette des intégrations
  (Chorus Pro, Yousign, GoCardless, Resend, EFI, SIRENE, VIES) demande des
  comptes configurés. Ce qui est prouvé ici : les écritures correspondent au
  schéma (scanner sur base réelle), les erreurs sont lues, l'entrée refuse sans
  identité, et les vérifications **locales** rendent le bon verdict.
* **`generate-pdf`** : rebrancher ou supprimer — c'est la décision `D-4` du
  registre, elle appartient au produit ; le défaut retenu est le plus sûr.
* **Playwright** : aucun parcours e2e ne couvre le dépôt électronique, la
  synchronisation bancaire ou la demande de signature — cinq parcours restent à
  écrire (phase 10), et ils exigent une application servie avec un jeu de
  données.
* Les autres défauts (**W5**, **W7**, **W8**, les **9 scénarios transverses**,
  les 62 chaînages) restent ouverts : W6 est la **phase 4**, parallélisable, et
  n'en ferme volontairement aucun.
