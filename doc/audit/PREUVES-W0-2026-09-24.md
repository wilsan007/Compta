## 4. W0.1 — le registre d'échecs attendus porte le couple (fichier, identifiant)

**Ce qui a été corrigé.** L'arbre portait la moitié du correctif : `_audit_expected` avait
bien été recréée en `(file, test_id, reason)`, mais `_audit_assert` comparait encore
`test_id` seul, et `expected_failures.sql` insérait deux colonnes dans une table à trois
colonnes `NOT NULL`. **Conséquence mesurée : toute suite d'audit échouait**, quelle que soit
la base. Les trois endroits comparent désormais le couple.

**La preuve, exécutée** (`sql/ci/audit_registry_selftest.sql`, branché en CI) :

| # | Exigence | Verdict |
|---|---|---|
| Z1 | un `T01` rouge dont le fichier **n'est pas** inscrit → `_audit_assert` lève | ✅ |
| Z2 | un `T01` vert dont le fichier **est** inscrit → `_audit_assert` lève (retirer la ligne) | ✅ |
| Z3 | un fichier sans verdict → `_audit_assert` lève | ✅ |
| Z4a | un rouge **inscrit** passe | ✅ |
| Z4b | un vert **non inscrit** passe | ✅ |

**Contre-épreuve (§4.7.3)** — l'ancienne clé est réinstallée dans une copie de travail
(`sed` : `e.test_id = ar.test_id`, sans le fichier), le même auto-test est rejoué :

```
❌ Z1  — attendu : échec « hors registre » pour TST-A → AUCUNE ERREUR
❌ Z4b — attendu : TST-D passe (vert non inscrit) → [TST-D] corrigé(s) mais encore au registre
ERROR: [AUD-X01] l'auto-test du registre a échoué : Z1, Z4b
```

C'est exactement le défaut décrit : **le `T01` du fichier B blanchissait celui du fichier
A**. L'auto-test n'est donc pas décoratif — il tombe quand la règle disparaît.

**Écart assumé avec le plan** : le plan allouait le numéro `235` à un fichier
`235_audit_registry_per_file.sql`. Aucune migration numérotée n'est écrite, et c'est
volontaire : `_audit_expected` est **recréée à chaque inclusion de `ci/audit_helpers.sql`**
(chaque fichier de test réinsère son registre dans la même session). Une migration ne
pourrait pas tenir ce contrat — elle s'exécuterait une fois, avant les tests, puis serait
écrasée. Le correctif appartient à `ci/audit_helpers.sql` et `ci/expected_failures.sql`.

## 6. W0.3 — les écritures dont l'erreur n'est jamais lue

`app/scripts/check-unchecked-writes.mjs` + `scripts/verify-rules/unchecked-writes.baseline.json`.

**Mesuré sur la base neuve** : **29 occurrences** (19 instructions distinctes), exactement le
total de l'audit du 23/09. Le gel porte sur le **nombre d'occurrences** de chaque instruction :
recopier une de ces écritures quelque part fait échouer la CI, même sans nouvelle instruction.

Les quatre alimentations de la paie sont dans la liste (`leavesAbsences.ts` : `leave_balances`
×1 et `payroll_variable_elements` ×4), avec les trois référentiels de cotisations
(`socialDeclarations.ts`), les trois anticipations de stock (`stock.ts`) et sept écritures
des webhooks (`outgoing-webhooks/index.ts`).

**Pourquoi ce n'est pas `audit-silent-failures.mjs`** : celui-ci cherche une déstructuration
*incomplète* (`const { data } = …` sans `error`). L'angle mort fermé ici est l'absence
**totale** de déstructuration — l'écriture échoue, personne ne lit, l'écran dit « enregistré ».

## 7. W0.4 — les politiques RLS permissives jumelles

`app/sql/ci/check_policy_duplicates.sql`.

**Mesuré sur la base neuve** : **1 739 politiques**, dont **495 couples (table, commande)
portant DEUX politiques permissives** sur **127 tables** — soit **1 001 politiques**. Le motif
est uniforme : une politique générique `tenant_select` (migration 74) **plus** une politique
par table `tenant_select_<table>` (migrations 84 et suivantes) qui, elle, porte la garde
`can_perform`. Deux politiques **permissives** sont OU-ées : la garde est donc inopérante.

**Le registre est gelé** avec les 127 tables et leurs verbes (`r`/`a`/`w`/`d`) : c'est le
périmètre exact de la migration 238. Deux échecs, pas un seul — un doublon **hors** registre
(ISO-03 revient), et une ligne de registre **devenue périmée** (le dédoublonnage a été fait :
la ligne doit être retirée dans le même commit).

**Auto-test intégré** : le contrôle crée une table temporaire à deux politiques permissives et
**exige de la voir** ; s'il est aveugle, il s'arrête avant de juger.

**Contre-épreuves exécutées** (les deux, en transaction, donc sans laisser de trace) :

| Contre-épreuve | Attendu | Obtenu |
|---|---|---|
| `CREATE POLICY zz_contre_epreuve ON currencies FOR SELECT` puis contrôle | échec, couple nommé | ✅ `currencies(r) ×2 → select_currencies + zz_contre_epreuve` |
| `DROP POLICY tenant_select_analytic_sections` puis contrôle | échec « registre périmé » | ✅ `analytic_sections(r) — retirer la ligne de ci/check_policy_duplicates.sql` |

Dans les deux cas le `ROLLBACK` a été vérifié : la politique de contre-épreuve est absente
après coup, et celle supprimée est bien restaurée.
