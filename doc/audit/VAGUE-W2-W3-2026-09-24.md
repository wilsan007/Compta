### 1.2 Ce que la 250 corrige

| Défaut | Correctif, dans la 250 |
|---|---|
| POS-01 (réécriture) | `prevent_pos_ticket_modification()` — déclencheur **BEFORE UPDATE**, volontairement **SECURITY INVOKER** : `current_user` y est l'appelant réel, ce qui distingue un appel direct (`authenticated`) d'une écriture faite par `void_pos_ticket()` (SECURITY DEFINER). Montants, date, numéro, empreinte, caisse, session, client : **immuables pour tout le monde**, propriétaire de la table compris. Seule exception : le rattachement d'une facture (`invoice_id`), qui ne réécrit rien de la vente. |
| POS-02 (lignes) | `prevent_pos_ticket_line_change()` — `UPDATE` et `DELETE` refusés (42501) ; l'`INSERT` reste ouvert tant que la session est ouverte et le ticket valide, sinon refusé (le ticket est figé à la clôture). |
| POS-03 (numéros) | `pg_advisory_xact_lock(hashtext('pos_ticket:<société>:<caisse>'))` avant la lecture de `MAX(sequential_number)`, et contrainte `pos_tickets_terminal_seq_unique UNIQUE (tenant_id, terminal_id, sequential_number)`. Les doublons déjà en base sont **réparés** par `pos_tickets_renumber_duplicates()` (renumérotation dans l'ordre de création **et recalcul des empreintes**, sinon `verify_pos_ticket_chain` déclarerait une base saine altérée) — une migration qui échoue sur les données réelles ne se déploie pas. |
| POS-04 (date) | `NEW.created_at := now()` dans le déclencheur de signature, et la société vient du contexte (`COALESCE(NEW.tenant_id, current_tenant_id())`, refus si NULL) : le hachage porte toujours la société réelle. La **date métier** (`date`) reste celle de l'appelant — un terminal hors ligne enregistre légitimement en différé — et c'est `created_at`, l'ancre du hachage, que le serveur pose. |
| statut non contraint | `CHECK (status IN ('completed','cancelled','refunded'))` ; les statuts NULL sont repris en `completed` (le ticket d'une vente qui a eu lieu, qui ne comptait dans aucune clôture), et un statut **inconnu fait échouer la migration en le nommant** : la reprise est une décision d'exploitation, pas un effacement silencieux. |
| pas de sortie honnête | `void_pos_ticket(p_ticket_id, p_reason)` : contrôle du rôle (`can_perform('pos_tickets','update')`), de la société (`current_tenant_id()`), du statut (« déjà annulé » refusé), et de la session (**clôturée → refus, avec le message qui dit d'émettre un avoir**) ; trace (`voided_at`, `void_reason`, `is_voided`) et **événement NF-525** `pos_ticket_voided` — le journal dit enfin qu'un ticket a changé. |

(W2, POS) et **251** (W3, chemins d'annulation). Le tableau de bord du plan est
mis à jour dans le même commit, et **il ne réserve plus aucun numéro pour la
suite** : `252` était déjà pris par le socle des chaînages
(`252_chain_socle.sql`) pendant que ces lignes s'écrivaient. Les vagues W4 → W9
reçoivent leur numéro **au moment de leur exécution**. C'est la seule
conséquence : aucun travail prévu n'est perdu, un numéro est une ressource
séquentielle, et le laisser deviner serait pire que le dire.

## 7. Incident de session — les fichiers `app/sql` non suivis, et leur restauration

**Ce qui s'est produit.** Pendant la session, le dossier `app/sql` a été remplacé
par une version antérieure (synchronisation externe — iCloud/Desktop : le dossier
parent a été modifié à 10:11 et `app/` à 10:14). Conséquence mesurée : les
fichiers **suivis** sont revenus à leur état `HEAD` (perdant quatre modifications
non commitées : `105_rls_tests.sql`, `236_…_tests.sql`,
`ci/check_policy_duplicates.sql`, `ci/expected_failures.sql`) et **les fichiers
non suivis ont disparu** : `237`, `238`, `239`, `245`, `246`, `247`, `248`,
`249`, `ci/check_composite_fks.sql`, `ci/check_roles_opposables.sql`.

**Ce qui les a sauvés.** Les *checkpoints* de l'éditeur, présents dans le dépôt :

```bash
git log --all --oneline --format='%h %ci %s'          # 5e37af8 (09:41) = l'arbre des fichiers suivis
git ls-tree -r --name-only e876c08                    # e876c08 = les 17 fichiers non suivis
git diff --name-only 5e37af8 | while read -r f; do    # restaurer l'état du 24/09 09:41
  mkdir -p "$(dirname "$f")"; git show "5e37af8:$f" > "$f"; done
git ls-tree -r --name-only e876c08 | while read -r f; do
  mkdir -p "$(dirname "$f")"; git show "e876c08:$f" > "$f"; done
```

`git status --short` a alors retrouvé **exactement** l'état d'entrée de la
session, et les quatre modifications récupérées sont mesurables :
`105` 23+/5-, `236` 107+/41-, `check_policy_duplicates` 34+/172-,
`expected_failures` 0+/7-.

**Ce que cela apprend, et qui reste écrit ici** : le travail de la vague W1
(237 → 249) vivait dans l'arbre de travail **sans être commité** — c'est
précisément ce que le plan appelle `AUD-X02` — et cela a failli coûter une
journée de mesures. Les deux vagues sont donc commitées avec leurs suites et
leur câblage CI dans le même commit (Definition of Done, points 3 et 4).
